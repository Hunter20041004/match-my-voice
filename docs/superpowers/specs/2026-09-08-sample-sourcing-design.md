# 素材來源重新設計

取代 `2026-09-05-source-picker-design.md` 的「來源選單」部分。該份文件的隱私邊界、
各來源規則、失敗備援仍然有效，這份只改「怎麼決定要拿哪些素材」。

## 為什麼改

舊設計開場先問「你想從哪裡拿到你平常怎麼表達的例子？」，列七個來源讓使用者選。

三個問題：

1. **這個問句本身就是門檻。** 多數人不知道自己該給什麼算是好樣本。
2. **列固定份數是碰運氣。** 一個 Drive 裡可能有幾百份文件，列十份等於隨機抽。
3. **拿到的樣本不一定適合要寫的東西。** 用申請表歸納出的口吻，拿去寫工作信件會不準。

## 核心改變

**不問「你要從哪拿素材」，改成用「你要寫什麼」反推該拿哪些素材。**

使用者來用這個技能，通常是因為手上有一件要寫的事。那件事同時是最好的篩選條件，
也保證找到的樣本跟要寫的東西屬於同一個場合。

## 流程

```
使用者：「幫我寫 XX」或「學我的口吻」
   │
   ├─ 沒說要寫什麼 → 問一句場合（求職申請／工作信件／社群貼文／報告心得）
   │
   ▼
偵測有沒有可用的連接器
   │
   ├─ 沒有 ─→ 直接走 B。不提服務，也不問。
   │
   └─ 有 ──→ 問一次：A 從服務找，還是 B 自己提供
              │
              ├─ A：拿「要寫什麼」當關鍵字去搜已連接的服務
              │     → 列候選，每份顯示：標題、日期、這份在講什麼
              │     → 摘要優先用搜尋回傳的片段；拿不到才讀該份開頭一小段
              │     → 使用者勾 3～5 份
              │     → 只讀勾中的，沒勾的不再碰
              │
              └─ B：貼上文字／上傳檔案／用這段對話／「我沒有，你問我」
   │
   ▼
問一句：「這幾份都是你自己寫的嗎？有沒有哪份是別人或 AI 幫你改很多的？」
   │
   ▼
分析 → 寫入口吻檔
```

## 候選清單怎麼列

**不列固定份數。** 用「要寫什麼」搜出來多少就是多少。

結果過多時以相關度排序，一次顯示到聊天視窗看得完為止（實作時以 15 份為預設上限），
並告訴使用者還有更多、可以要求下一批或縮小描述。不要靜靜截斷。

每份顯示三件事：**標題、日期、這份在講什麼**。

「這份在講什麼」是這次設計的關鍵——它取代了「這份是不是他自己寫的」當作判斷依據。
使用者看到「這份在講你的實習申請動機」，自己就知道是不是他寫的、適不適合。

摘要來源分兩級：

1. 搜尋結果本身帶回的片段——有就用，零額外成本
2. 拿不到才讀該份開頭一小段

排除：試算表、簡報、圖片。只留文件類型。

若服務能分辨檔案擁有者，優先只列使用者自己建立的。分辨不了就照列，靠「這份在講什麼」
和最後那句人工確認擋。

## 口吻檔的兩層結構

| 層 | 內容 | 例子 |
|---|---|---|
| **核心** | 不分場合都成立的習慣 | 「不要用助理代寫的宣傳腔」「具體，不抽象」 |
| **場合模式** | 這個場合的他 | 求職自傳的他／工作信件的他／社群貼文的他 |

「正式的他」也是他，不是跟他的口吻打架。所以不需要在「照口吻」和「照場合」之間取捨。

**口吻檔必須記錄自己驗證過哪些場合。** 這是第二次使用時的判斷依據。

## 第二次使用

- 這次的場合，口吻檔已涵蓋 → 直接寫，不重新找素材
- 沒涵蓋 → 只針對這個場合回去找樣本，核心層沿用
- 找不到該場合的樣本 → 用核心層加上一般的正式寫法，並明講：

  > 「你沒有這個場合的樣本，所以我用一般的正式寫法，只保留你核心的習慣。
  > 寫出來哪裡不像你，跟我說，我記起來。」

不假裝知道，也不擋著不寫。第一次靠猜，之後靠使用者修。

## 樣本不夠時

照做，但把口吻檔標成暫定，並明確說出缺什麼：

> 「這份只靠得住短文，長文可能不準。」

不擋人——擋下來要使用者補到夠，正是讓人放棄的門檻。也不講大話。

## 原文的保留範圍

**只留摘錄，不留全文。** 每份抽幾句具代表性的存進口吻檔當證據。

理由：口吻檔本來就需要例句支撐（不然無法說明歸納的根據），留摘錄順便解決了
「事後說不出根據」的問題；但不等於在使用者電腦上複製一份他的完整文件。

## 範圍

規則寫成通用的「已連接的服務」，Google Drive 當作寫得最詳細的那個範例。
不寫任何服務專屬的 API 指令，不新增相依套件。

## 不做什麼

- 不自動掃描整個帳號或整顆硬碟
- 不在沒有連接器的環境提起任何服務名稱
- 不把使用者沒勾選的檔案讀完
- 不因為使用者選了某個服務，就認為可以編輯、寄送、上傳或發布
- 不做多語言口吻的合併（不同語言各自一份）

## 未驗證項

**連接器是否暴露「這份檔案是不是使用者自己建立的」欄位，未經實測。**

Google Drive API 本身有 `ownedByMe`，但各家連接器包不包這個欄位無法一概而論；
設計此份文件時的環境沒有安裝任何 Drive 連接器，無法驗證。

因此本設計不依賴這個欄位：拿得到就用來過濾，拿不到就靠「這份在講什麼」加上
最後的人工確認。實作時若確認拿得到，可以把候選清單品質再提高一階。

## 驗收檢查

一次驗一項：

1. 沒有任何連接器時，不出現服務選項，也不詢問要不要串接。
2. 使用者說「幫我寫求職信」時，不再出現舊版那個列七個來源的開放式問句。
   （有連接器時仍會出現一次「A 從服務找／B 自己提供」的二選一，這是預期行為。）
3. 使用者只說「學我的口吻」時，先問場合，才開始找素材。
4. 候選清單每一列都有「這份在講什麼」。
5. 沒被勾選的檔案，不會被完整讀取。
6. 分析前一定出現一次作者確認。
7. 樣本不足時仍產出口吻檔，且該檔標記為暫定並寫出缺口。
8. 口吻檔中可以看出它驗證過哪些場合。
9. 第二次使用且場合已涵蓋時，不重新尋找素材。
10. 口吻檔內只有摘錄，沒有任何來源文件的全文。

這些檢查證明流程照設計運作，**不證明產出的文字真的像本人**。後者仍以
`docs/first-pilot-zh-TW.md` 的多人盲測為準。
